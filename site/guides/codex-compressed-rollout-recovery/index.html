Codex 会话只剩 .jsonl.zst：Watch 的读取边界与恢复路径

Codex 压缩本地线程后，原 rollout 只剩 .jsonl.zst；Watch 不读压缩格式，这些会话不会出现在任何列表里。用 watch doctor 看「读不出目录归属」的数量，并在 Codex 里继续该线程触发重新展开。副本是 0 字节时内容已丢失，只能从备份恢复；不要删除或改名 .zst 文件。

Watch 只读取 ~/.codex/sessions 下未压缩的 rollout .jsonl；文件被 Codex 压缩后原 .jsonl 不在、只剩同名 .jsonl.zst，这些会话无法被列出、解析或交接。watch doctor 与列表命令会披露数量，而不是假装它们不存在。若副本确实由 Codex 压缩且内容完好，可尝试在 Codex 里继续该会话并确认 .jsonl 是否重新出现。

发布日期: 2026-11-23 更新日期: 2026-11-23 适用版本: Watch v0.1.386
核心判断依据

Watch 读取的是 ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl 这类未压缩文件。Codex 压缩本地线程后，原文件不在，同目录只剩同名 .jsonl.zst（例如 rollout-....jsonl.zst）。Watch 不解压、不改写，也不会把「读不出来」讲成「没有这条会话」：列表、status、doctor 与 search 都会披露这一档的数量，并说明它们无法归属到任何目录。

Codex 的会话归属写在 rollout 首行 session_meta 的 cwd 字段里，而压缩副本无法读取首行，Watch 因此无法判断它属于哪个工作目录。这就是 watch doctor 的「读不出目录归属」与 watch sessions 的 unattributable 字段：它们不是错误，而是「这些文件存在，但这一版看不到里面的内容」。同一台机器上积累大量压缩历史时，这个数量可能很大，属于正常现象。

副本有两种状态，下一步相反。非空副本：如果确实是 Codex 的本地线程压缩且副本完好，在 Codex 里继续该会话可能重新展开为 .jsonl，之后 Watch 才能读取。0 字节副本：内容已经丢失，重新展开也拿不回对话，只能从备份恢复或当作新会话处理。Watch 只 stat 副本是否存在、是否 0 字节，不打开、不解压，因此披露里写的是「若是 Codex 的本地线程压缩且副本完好」。

  1. 步骤 1：确认数量与文件形态

    执行 watch doctor --json：storage 里 codex 一行的 count 只统计可读会话，unattributable 给出压缩副本等读不出归属的文件数；文本模式会在会话数旁显示「另有 M 个文件读不出目录归属」。watch sessions --json 与 watch recent --json 带同名字段。警告里会按文件形态写明「只有 .jsonl.zst 压缩副本」或「0 字节的同名压缩副本」，两种情况下一步不同。

  2. 步骤 2：区分非空副本与 0 字节副本

    找到对应的 .jsonl.zst。非空只说明还有字节，不代表副本完好或可解压；0 字节则说明这份副本没有可恢复的内容，需另找备份。如果该会话是不可用的链尾，watch doctor --json 的 store.brokenTips[].compressedPath 给出副本路径，compressedEmpty 为 true 表示 0 字节。列表的 unattributable 只给文件数。

  3. 步骤 3：在 Codex 里继续该会话

    在 Codex 中打开或继续该线程。若副本是 Codex 的本地线程压缩且完好，Codex 会把它重新展开为 .jsonl；回到终端执行 watch sessions，这条会话就会重新出现，status / switch / open 也能读到。Watch 不会替你触发展开，也不会改 .zst。

  4. 步骤 4：展开后再交接

    拿到重新展开的会话 id 后，按常规路径交接：watch open <id> --to <provider> 或 watch switch <provider>。watch prompt 也不读压缩文件；显式指定该会话时会报错，不生成交接文档。

# 1. 只读：数量与原因 npm run watch -- doctor --json npm run watch -- sessions --json # 2. 找到具体文件（原 .jsonl 不在、只剩同名 .zst） ls ~/.codex/sessions/*/*/*/*.jsonl.zst # 3. 在 Codex 里继续该会话，让它重新展开；随后 Watch 可列出 npm run watch -- sessions --json # 4. 展开后再交接 npm run watch -- open <session-id> --to <provider>
边界与不要做的事

1. Watch 不解压、不改写、不删除 .jsonl.zst，也不会替你判断内容是否可解；它只 stat 副本是否存在、是否 0 字节。 2. .zst 也可能是你自己归档的，Watch 不假定压缩一定是 Codex 做的；「在 Codex 里继续会重新展开」只在确实是 Codex 本地线程压缩且副本完好时成立。 3. 不要手工解压后放回 sessions 目录：Watch 不校验这种手写文件的形状，Codex 是否接受也没有验证记录。 4. 不要直接删除或改名 .zst：那是你的原生会话数据，删掉后没有任何恢复路径。 5. 本指南依据本地文件与 Watch 的披露行为；原生客户端是否接受展开后的会话，按各自版本与平台单独验收，本指南不构成原生验收。

常见问题与限制

Watch 会把我的 Codex 会话压缩或删掉吗？

不会。压缩是 Codex 自己的行为；Watch 不读取、改写或删除 .zst；列出和解析会话时读的是未压缩的 .jsonl。以 Codex 为目标的写入式交接是另一回事，可能新建或更新目标端未压缩的会话文件。

为什么 doctor 说「读不出目录归属」，而不是直接说文件被压缩了？

因为 Watch 只 stat、不打开压缩文件：它能确认原 .jsonl 不在、同名 .zst 在，并把这一档按「压缩副本」写进警告，但无法确认副本内容是否可解，也无法读出 Codex 归属所在的 session_meta 首行。措辞里保留「若是 Codex 的本地线程压缩且副本完好」就是为了不替未验证的事实背书。

能自己把 .zst 解压回 .jsonl 吗？

不推荐。那是原生存储目录，手写文件的形状 Watch 不校验，Codex 是否接受也没有验证记录；最稳妥的路径是在 Codex 里继续该会话，让原生自己展开。

0 字节副本和完好副本有什么区别？

0 字节副本内容已经丢失，重新展开也拿不回对话，只能从备份恢复或当作新会话；完好副本在 Codex 里继续时可能被重新展开为 .jsonl，之后 Watch 就能读取。

这些压缩会话还能交接给别的 Agent 吗？

不能直接交接。先让 Codex 重新展开，再按常规路径用 watch open <id> --to <provider> 或 watch switch。交接前仍建议核对工作目录与会话 id，并阅读结果里的 warnings。
