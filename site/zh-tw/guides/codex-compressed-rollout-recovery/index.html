Codex 會話只剩 .jsonl.zst：Watch 的讀取邊界與恢復路徑

Codex 壓縮本機執行緒後，原 rollout 只剩 .jsonl.zst；Watch 不讀壓縮格式，這些會話不會出現在任何列表裡。用 watch doctor 看「讀不出目錄歸屬」的數量，並在 Codex 裡繼續該執行緒以觸發重新展開。副本是 0 位元組時內容已遺失，只能從備份還原；不要刪除或改名 .zst 檔案。

Watch 只讀取 ~/.codex/sessions 下未壓縮的 rollout .jsonl；檔案被 Codex 壓縮後，原 .jsonl 不在、只剩同名 .jsonl.zst，這些會話無法被列出、解析或交接。watch doctor 與列表命令會揭露數量，而不是假裝它們不存在。若副本確實由 Codex 壓縮且內容完好，可嘗試在 Codex 裡繼續該會話，並確認 .jsonl 是否重新出現。

發布日期: 2026-11-23 更新日期: 2026-11-23 適用版本: Watch v0.1.432
核心判斷依據

Watch 讀取的是 ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl 這類未壓縮檔案。Codex 壓縮本機執行緒後，原檔案不在，同目錄只剩同名 .jsonl.zst（例如 rollout-....jsonl.zst）。Watch 不解壓、不改寫，也不會把「讀不出來」講成「沒有這條會話」：列表、status、doctor 與 search 都會揭露這一檔的數量，並說明它們無法歸屬到任何目錄。

Codex 的會話歸屬寫在 rollout 首列 session_meta 的 cwd 欄位裡，而壓縮副本無法讀取首列，Watch 因此無法判斷它屬於哪個工作目錄。這就是 watch doctor 的「讀不出目錄歸屬」與 watch sessions 的 unattributable 欄位：它們不是錯誤，而是「這些檔案存在，但這一版看不到裡面的內容」。同一台機器上累積大量壓縮歷史時，這個數量可能很大，屬於正常現象。

副本有兩種狀態，下一步相反。非空副本：如果確實是 Codex 的本機執行緒壓縮且副本完好，在 Codex 裡繼續該會話可能重新展開為 .jsonl，之後 Watch 才能讀取。0 位元組副本：內容已經遺失，重新展開也拿不回對話，只能從備份還原或視為新會話處理。Watch 只 stat 副本是否存在、是否 0 位元組，不開啟、不解壓，因此揭露裡寫的是「若是 Codex 的本機執行緒壓縮且副本完好」。

  1. 步驟 1：確認數量與檔案形態

    執行 watch doctor --json：storage 裡 codex 那一列的 count 只統計可讀會話，unattributable 給出壓縮副本等讀不出歸屬的檔案數；文字模式會在會話數旁顯示「另有 M 個檔案讀不出目錄歸屬」。watch sessions --json 與 watch recent --json 帶同名字段。警告裡會依檔案形態寫明「只有 .jsonl.zst 壓縮副本」或「0 位元組的同名壓縮副本」，兩種情況下，下一步不同。

  2. 步驟 2：區分非空副本與 0 位元組副本

    找到對應的 .jsonl.zst。非空只代表還有位元組，不代表副本完好或可解壓；0 位元組則代表這份副本沒有可恢復的內容，需另找備份。如果該會話是不可用的鏈尾，watch doctor --json 的 store.brokenTips[].compressedPath 給出副本路徑，compressedEmpty 為 true 表示 0 位元組。列表的 unattributable 只給檔案數。

  3. 步驟 3：在 Codex 裡繼續該會話

    在 Codex 中開啟或繼續該執行緒。若副本是 Codex 的本機執行緒壓縮且完好，Codex 會把它重新展開為 .jsonl；回到終端機執行 watch sessions，這條會話就會重新出現，status / switch / open 也能讀到。Watch 不會替你觸發展開，也不會改 .zst。

  4. 步驟 4：展開後再交接

    拿到重新展開的會話 id 後，依常規路徑交接：watch open <id> --to <provider> 或 watch switch <provider>。watch prompt 也不讀壓縮檔案；明確指定該會話時會報錯，不產生交接文件。

# 1. 唯讀：數量與原因 npm run watch -- doctor --json npm run watch -- sessions --json # 2. 找到具體檔案（原 .jsonl 不在、只剩同名 .zst） ls ~/.codex/sessions/*/*/*/*.jsonl.zst # 3. 在 Codex 裡繼續該會話，讓它重新展開；隨後 Watch 可列出 npm run watch -- sessions --json # 4. 展開後再交接 npm run watch -- open <session-id> --to <provider>
邊界與不要做的事

1. Watch 不解壓、不改寫、不刪除 .jsonl.zst，也不會替你判斷內容是否可解；它只 stat 副本是否存在、是否 0 位元組。 2. .zst 也可能是你自己封存的，Watch 不假定壓縮一定是 Codex 做的；「在 Codex 裡繼續會重新展開」只在確實是 Codex 本機執行緒壓縮且副本完好時成立。 3. 不要手動解壓後放回 sessions 目錄：Watch 不驗證這種手寫檔案的形狀，Codex 是否接受也沒有驗證紀錄。 4. 不要直接刪除或改名 .zst：那是你的原生會話資料，刪掉後沒有任何恢復路徑。 5. 本指南依據本機檔案與 Watch 的揭露行為；原生用戶端是否接受展開後的會話，依各自版本與平台單獨驗收，本指南不構成原生驗收。

常見問題

Watch 會把我的 Codex 會話壓縮或刪掉嗎？

不會。壓縮是 Codex 自己的行為；Watch 不讀取、不改寫、不刪除 .zst；列出和解析會話時讀的是未壓縮的 .jsonl。以 Codex 為目標的寫入式交接是另一回事，可能建立或更新目標端未壓縮的會話檔案。

為什麼 doctor 說「讀不出目錄歸屬」，而不是直接說檔案被壓縮了？

因為 Watch 只 stat、不開啟壓縮檔案：它能確認原 .jsonl 不在、同名 .zst 在，並把這一檔依「壓縮副本」寫進警告，但無法確認副本內容是否可解，也無法讀出 Codex 歸屬所在的 session_meta 首列。措辭裡保留「若是 Codex 的本機執行緒壓縮且副本完好」，就是不替未驗證的事實背書。

能自己把 .zst 解壓回 .jsonl 嗎？

不建議。那是原生儲存目錄，手寫檔案的形狀 Watch 不驗證，Codex 是否接受也沒有驗證紀錄；最穩妥的路徑是在 Codex 裡繼續該會話，讓原生自己展開。

0 位元組副本和完好副本有什麼區別？

0 位元組副本內容已經遺失，重新展開也拿不回對話，只能從備份還原或視為新會話；完好副本在 Codex 裡繼續時可能被重新展開為 .jsonl，之後 Watch 就能讀取。

這些壓縮會話還能交接給別的 Agent 嗎？

不能直接交接。先讓 Codex 重新展開，再依常規路徑用 watch open <id> --to <provider> 或 watch switch。交接前仍建議核對工作目錄與會話 id，並閱讀結果裡的 warnings。
