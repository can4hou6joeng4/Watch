Codex Sessions Left as .jsonl.zst: Watch Read Boundaries and Recovery

After Codex compresses a local thread, the rollout remains only as a .jsonl.zst; Watch does not read the compressed format, so the session appears in no list. Use watch doctor to see the unattributable count and continue the thread in Codex to trigger re-expansion. A zero-byte copy has lost its content; restore from backup. Do not delete or rename the .zst file.

Watch reads uncompressed rollout .jsonl files under ~/.codex/sessions. After Codex compresses a local thread, the original .jsonl is gone and only a same-name .jsonl.zst remains; those sessions cannot be listed, parsed or handed off. watch doctor and the list commands disclose the count instead of pretending they do not exist. If Codex compressed the file and the copy is intact, try continuing the session in Codex and check whether the .jsonl reappears.

Published: 2026-11-23 Modified: 2026-11-23 Applies to: Watch v0.1.311
Key Distinction

Watch reads uncompressed files such as ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl. After Codex compresses a local thread, the original file is gone and only a same-name .jsonl.zst remains in the same directory. Watch does not decompress or rewrite it, and it does not report unreadable as nonexistent: lists, status, doctor and search all disclose the count and say these files cannot be attributed to any directory.

Codex stores session attribution in the cwd field of the first session_meta line, and a compressed copy cannot have that line read. Watch therefore cannot tell which working directory the session belongs to. That is what the unattributable count in watch doctor and the unattributable field in watch sessions report: not an error, but files that exist while this version cannot see inside them. Large compressed histories can produce a large count, and that is expected.

A copy has two states with opposite next steps. For a nonempty copy, continuing the session in Codex may re-expand it into .jsonl if Codex made the copy and it is intact. Watch can read the plain file after it reappears. A zero-byte copy has lost its content; re-expansion cannot bring the conversation back, so restore from backup or treat it as a new session. Watch only stats whether a copy exists and whether it is zero bytes; it never opens or decompresses it, which is why the disclosure says it holds only if the copy is intact Codex compression.

  1. Step 1: Check the count and file shape

    Run watch doctor --json. For codex, count includes only readable sessions while unattributable counts files whose directory cannot be read, such as compressed copies. The text output shows the unattributable total next to the session count. watch sessions --json and watch recent --json carry the same field. The warning names the shape: a same-name .jsonl.zst compressed copy, or a zero-byte same-name copy. The two call for different next steps.

  2. Step 2: Distinguish nonempty copies from zero-byte copies

    Find the matching .jsonl.zst. A nonempty file still has bytes, but that does not prove it is intact or can be decompressed. A zero-byte copy holds no recoverable content; look for a backup. If the session is an unusable chain tip, watch doctor --json shows the copy path in store.brokenTips[].compressedPath and sets compressedEmpty to true for a zero-byte copy. The list field unattributable only reports counts.

  3. Step 3: Continue the session in Codex

    Open or continue the thread in Codex. If the copy is intact Codex local thread compression, Codex re-expands it into .jsonl. Run watch sessions afterward and the session appears again; status, switch and open can read it too. Watch never triggers the re-expansion and never touches the .zst.

  4. Step 4: Hand off after re-expansion

    Once you have the re-expanded session id, use the usual paths: watch open <id> --to <provider> or watch switch <provider>. watch prompt does not read the compressed file either. If you specify that session, it reports an error and produces no handoff document.

# 1. Read-only: count and cause npm run watch -- doctor --json npm run watch -- sessions --json # 2. Find the files (the original .jsonl is gone; only .zst remains) ls ~/.codex/sessions/*/*/*/*.jsonl.zst # 3. Continue the session in Codex to re-expand it; Watch can then list it npm run watch -- sessions --json # 4. Hand off after re-expansion npm run watch -- open <session-id> --to <provider>
Boundaries and What Not To Do

1. Watch does not decompress, rewrite or delete .jsonl.zst, and it does not judge whether the content can be decoded; it only stats existence and zero size. 2. A .zst file may also be your own archive. Watch does not assume Codex produced it, so the re-expansion path holds only for intact Codex local thread compression. 3. Do not decompress by hand and put the result back into the sessions directory: Watch does not validate hand-made files, and Codex acceptance has no verification record. 4. Do not delete or rename the .zst: it is your native session data, and deleting it leaves no recovery path. 5. This guide follows local files and Watch disclosure behavior. Whether a native client accepts a re-expanded session is validated per version and platform separately, and this guide is not native acceptance.

Frequently Asked Questions

Does Watch compress or delete my Codex sessions?

No. Compression is Codex behavior. Watch does not read, rewrite, or delete .zst files; listing and parsing use uncompressed .jsonl. A write-enabled handoff into Codex is separate and may create or update an uncompressed target session file.

Why does doctor say the directory cannot be attributed instead of saying the file is compressed?

Because Watch only stats the compressed file and never opens it. It can confirm the original .jsonl is gone and a same-name .zst exists, and its warning names that compressed-copy case, but it cannot confirm the copy decodes or read the session_meta first line that holds attribution. The wording stays conditional so it does not vouch for an unverified fact.

Can I decompress the .zst back into a .jsonl myself?

Not recommended. That is the native storage directory; Watch does not validate hand-made files, and Codex acceptance has no verification record. The safer path is continuing the session in Codex and letting the native client re-expand it.

What is the difference between a zero-byte copy and an intact copy?

A zero-byte copy has lost its content; re-expansion cannot bring the conversation back, so restore from backup or treat it as a new session. An intact copy may be re-expanded when you continue the session in Codex, after which Watch can read it.

Can these compressed sessions still be handed off to another agent?

Not directly. Re-expand in Codex first, then use watch open <id> --to <provider> or watch switch. Before handing off, still check the session id and working directory and read the warnings in the result.
