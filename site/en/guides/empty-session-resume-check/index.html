Why resume Opens an Empty Session: Detecting and Recovering 0-Turn Sessions

An empty session after resume usually means the file has no turns left: a legitimate empty session created by watch new, content cleared with only a placeholder header left, or a zero-byte file. Check the turn count on the chain-tip row in watch status. Watch does not rebuild history for you; restore the file from backup, rebind to another session, or start a new chain.

Watch hands the chain-tip session and its working directory to the target tool; the resume command itself only opens the session. This guide starts from the chain-tip row in status, separates readable 0-turn sessions from zero-byte files, and gives three recovery paths: backup restore, rebinding with adopt, and a new chain.

Published: 2026-11-17 Modified: 2026-11-23 Applies to: Watch v0.1.490
Key Distinction

A resume command, and the native resume command of each client, does one thing: open the specified session. Whether it can continue depends on how many turns remain in that file. Existing and readable do not mean it has content, which is exactly how a resume opens into an empty session while everything looks fine. Watch discloses this case separately in open, switch, new and status.

There are two kinds of empty. A readable 0-turn file still has a valid session header (the placeholder user line in Claude Code, the session_meta line in a Codex rollout) but no conversation turns. A zero-byte file was killed mid-write, ran out of disk, or was truncated, so even the session metadata may be gone; Codex stores attribution in the first rollout line, so truncating to zero bytes also breaks lookup.

A third way to open an empty session is that the file no longer exists. Claude Code deletes transcripts older than cleanupPeriodDays after a session starts; the official default is 30 days, and the key is allowed in any settings file, so project settings can override user settings. Expired sessions no longer appear in /resume, and watch open or resume cannot find them either. watch doctor reads, without writing, your user settings, the current directory project settings and, inside a subdirectory of a normal Git repository, the repository-root local settings (scope repository-local), and warns when a value is below the default or cannot be confirmed. It does not present that value as the effective one, and --settings plus managed settings are out of scope. Raising the retention period only reduces future deletions; it does not restore files already removed, so back up important sessions in advance.

  1. Step 1: Read the chain-tip row in status

    Run watch status. The chain-tip row shows its turn count, for example a chain tip with 12 turns; a 0-turn parse says it parsed 0 turns and points at the warning above; an unreadable or missing file carries no count. In JSON the fields are chainTipTurns and chainTipEmpty, and chainTipTurns exists only when the parse succeeds. When a 0-turn tip has unparsable lines, the same result also carries chainTipBadLines (or chains[].tip.badLines in chain list --json) with a count and, if the scan failed, an error; the text tip row says the file has bad lines instead of calling it an empty session. In doctor --json, a store.emptyTips[] entry with bad lines carries that same badLines field. With several chains, the tip row in watch chain list carries the same count; when in doubt, store.emptyTips in watch doctor lists tips that parse to 0 turns. watch new --json also reports the actual parsed turn count: claude and pi write a placeholder user message, so it shows 1 turn, while codex, grok and opencode show 0. watch usage separates a 0-turn empty session from a session that has content but no recorded usage. Unparsable content lines, Codex compaction records, a deleted content file with sidecar usage still readable, and bad lines beside existing turns are each disclosed with their own reason. A failed scan says the bad-line count is unknown, and a 0-turn summary does not add a usage-counted clause.

  2. Step 2: Read the five warning cases

    The same result separates zero bytes (the session file is empty), readable 0 turns (parsed 0 turns, nothing to continue), unreadable content (permissions or content), a missing file (deleted or moved), and a failed content parse (the file reads fine, but the session format is damaged or the OpenCode database is missing its message table; the warning says the content failed to parse and Watch could not verify the turn count or tail state). Each case has a different next step; do not rebind just because you saw the word empty. The last case does not even tell you whether the session is empty, so do not treat it as an empty session: run watch switch or watch open once and let the preflight report the specific reason.

  3. Step 3: Check whether it is a brand-new empty session

    A session created by watch new is empty by design. It is the normal starting point for a first chain: the next switch or open --to uses it as the target and merges the source content in. If the chain tip is that new session and you have not switched yet, 0 turns is expected, not damage.

  4. Step 4: Recover according to the case

    Content cleared: restore the file from backup and retry resume; Watch does not rebuild history. Wrong session: rebind the chain tip with watch adopt <provider> --session <another-session-id>. Keep both sides: start another chain with watch chain new <new-chain-name> and leave the original records untouched. Zero bytes with no backup: nothing is left to recover, treat it as a new session.

# 1. Read the chain-tip turn count and warnings npm run watch -- status --json # 2. Three paths when the chain tip is an empty session npm run watch -- adopt <provider> --session <another-session-id> # rebind to another session npm run watch -- chain new <new-chain-name> # start another chain # 3. Restore from backup first, then retry resume npm run watch -- switch <provider>
Boundaries

1. Watch does not rebuild history: a 0-turn session can only come back from your own backup. 2. Watch never deletes or repairs a zero-byte file on its own; that is your native session file, and the decision to restore or abandon it is yours. 3. A readable 0-turn session is not necessarily cleared content: watch new creates exactly that shape, so judge by context, not by the number alone. 4. These disclosures come from reading local files; they do not guarantee that the native client will open the session, and client acceptance stays recorded per version and platform.

Frequently Asked Questions

Did Watch lose the history when resume opened an empty session?

Usually not. Watch reads the source first and appends to the target with write guards and atomic writes; a 0-turn session is usually empty from the start (a new session from watch new) or was cleared or truncated earlier. To check whether a Watch write caused it, compare the turn count and warnings in the handoff result with your backup file.

What is the difference between 0 turns and 0 bytes?

0 turns means the file is readable and has a valid session header but no conversation; it may be a new session or only a placeholder header left behind. 0 bytes means the file itself is empty, from a killed process, a full disk or a half write, and even the session metadata may be gone. The first may just not have started; the second should send you to backups first.

Can Watch restore a cleared session automatically?

No. Watch only reads and writes local session files. It has no history backup and does not invent conversation. Recovery comes from your own backup (Time Machine, copies outside the repo, editor history), and you resume after restoring the file.

Does Claude Code delete old sessions on its own?

Yes. cleanupPeriodDays in the official settings reference defaults to 30 days; after a session starts, Claude Code sweeps transcripts older than that in the background, and expired sessions stop appearing in /resume. The key is allowed in any settings file, so project settings can override user settings. watch doctor reads your user settings, the current directory project settings and the repository-root local settings without writing, but --settings and managed settings are out of scope, so the report is not the effective value. Raising the value only reduces future deletions; it cannot bring back files already removed.
