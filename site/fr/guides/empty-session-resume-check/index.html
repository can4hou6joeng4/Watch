Pourquoi la reprise ouvre une session vide : détecter et récupérer les sessions à 0 tour

Une session vide après la reprise signifie généralement que le fichier n'a plus de tours : une session vide légitime créée par watch new, un contenu effacé ne laissant qu'un en-tête factice, ou un fichier de 0 octet. Vérifiez le nombre de tours sur la ligne de pointe de chaîne dans watch status. Watch ne reconstruit pas l'historique à votre place ; restaurez le fichier depuis une sauvegarde, rattachez une autre session, ou démarrez une nouvelle chaîne.

Watch remet la session de pointe de chaîne et son répertoire de travail à l'outil cible ; la commande de reprise elle-même ne fait qu'ouvrir la session. Ce guide part de la ligne de pointe de chaîne dans status, distingue les sessions à 0 tour lisibles des fichiers de 0 octet et propose trois voies de récupération : restauration depuis une sauvegarde, rattachement avec adopt et nouvelle chaîne.

Publié: 2026-11-17 Modifié: 2026-11-23 S’applique à: Watch v0.1.318
Distinction clé

Une commande de reprise, y compris la commande native de chaque client, ne fait qu'une chose : ouvrir la session indiquée. La poursuite dépend du nombre de tours restant dans ce fichier. Existant et lisible ne signifient pas qu'il y a du contenu — c'est précisément pourquoi une reprise s'ouvre sur une session vide alors que tout semble normal. Depuis v0.1.84, Watch dévoile ce cas séparément dans open, switch, new et status.

Il y a deux sortes de vide. Un fichier à 0 tour lisible a encore un en-tête de session valide (la ligne user factice dans Claude Code, la ligne session_meta dans un rollout Codex) mais aucun tour de conversation. Un fichier de 0 octet a été tué en cours d'écriture, a manqué d'espace disque ou a été tronqué ; même les métadonnées de session peuvent manquer. Codex stocke l'attribution dans la première ligne du rollout, donc une troncature à zéro octet casse aussi la recherche.

Une troisième façon d'ouvrir une session vide est que le fichier n'existe plus. Claude Code supprime les transcriptions plus anciennes que cleanupPeriodDays après le début d'une session ; la valeur officielle par défaut est de 30 jours, et la clé est admise dans tout fichier de réglages, si bien que les réglages de projet peuvent écraser ceux de l'utilisateur. Les sessions expirées n'apparaissent plus dans /resume, et watch open ou resume ne les trouve pas non plus. watch doctor lit sans écrire vos réglages utilisateur, les réglages de projet du répertoire courant et, dans un sous-répertoire d'un dépôt Git normal, les réglages locaux à la racine du dépôt (scope repository-local), et avertit lorsqu'une valeur est inférieure à la valeur par défaut ou ne peut être confirmée. Il ne présente pas cette valeur comme effective, et --settings ainsi que les réglages gérés sont hors périmètre. Augmenter la rétention ne réduit que les suppressions futures ; elle ne restaure pas les fichiers déjà supprimés, sauvegardez donc les sessions importantes à l'avance.

  1. Étape 1 : lire la ligne de pointe de chaîne dans status

    Exécutez watch status. Depuis v0.1.90, la ligne de pointe de chaîne affiche son nombre de tours, par exemple une pointe de chaîne à 12 tours ; un fichier parsé à 0 tour indique qu'il a parsé 0 tour et renvoie à l'avertissement ci-dessus ; un fichier illisible ou manquant ne porte aucun nombre. En JSON, les champs sont chainTipTurns et chainTipEmpty, et chainTipTurns n'existe que lorsque le parsing réussit. Avec plusieurs chaînes, la ligne de pointe de watch chain list porte le même nombre (v0.1.93) ; en cas de doute, store.emptyTips dans watch doctor liste les pointes parsées à 0 tour (v0.1.92). watch new --json rapporte aussi le nombre de tours réellement parsé (v0.1.94) : claude et pi écrivent un message user factice, donc 1 tour, tandis que codex, grok et opencode affichent 0. Depuis v0.1.95, watch usage distingue une session vide à 0 tour d'une session avec contenu mais sans usage enregistré, une chaîne fraîchement créée n'est donc plus signalée comme lacune statistique. Depuis v0.1.96, les lignes de contenu non parsables et les enregistrements de compaction Codex ne sont plus signalés à tort comme sessions vides. Depuis v0.1.97, un fichier de contenu supprimé est dévoilé même lorsque l'usage sidecar reste disponible. Depuis v0.1.98, les lignes de contenu défectueuses sont dévoilées dans warnings et les champs au lieu de rester silencieuses ; depuis v0.1.99, une ligne défectueuse avec des tours existants n'est plus décrite comme un parsing à 0 tour ; depuis v0.1.100, le résumé texte sépare les sessions à 0 tour des sessions avec usage, et un scan échoué dit que le nombre de lignes défectueuses est inconnu ; depuis v0.1.101, le résumé à 0 tour n'ajoute plus de clause de comptage d'usage, et la note v0.1.98 décrit une lacune de divulgation plutôt qu'un usage perdu.

  2. Étape 2 : lire les cinq cas d'avertissement

    Le même résultat sépare zéro octet (le fichier de session est vide), 0 tour lisible (0 tour parsé, rien à poursuivre), contenu illisible (permissions ou contenu), fichier manquant (supprimé ou déplacé), et parsing de contenu échoué (le fichier se lit bien, mais le format de session est endommagé ou la base OpenCode n'a pas de table message ; depuis v0.1.279, l'avertissement indique que le contenu n'a pas pu être parsé et que Watch n'a pas pu vérifier le nombre de tours ni l'état de la fin). Chaque cas appelle une étape différente ; ne rattachez pas simplement parce que le mot vide apparaît. Le dernier cas ne dit même pas si la session est vide : ne le traitez pas comme une session vide, exécutez une fois watch switch ou watch open et laissez la pré-vérification rapporter la raison précise.

  3. Étape 3 : vérifier s'il s'agit d'une session vide toute neuve

    Une session créée par watch new est vide par conception. C'est le point de départ normal d'une première chaîne : le switch ou open --to suivant l'utilise comme cible et y fusionne le contenu source. Si la pointe de chaîne est cette nouvelle session et que vous n'avez pas encore fait de switch, 0 tour est attendu, pas un dommage.

  4. Étape 4 : récupérer selon le cas

    Contenu effacé : restaurez le fichier depuis une sauvegarde et réessayez la reprise ; Watch ne reconstruit pas l'historique. Mauvaise session : rattachez la pointe de chaîne avec watch adopt <provider> --session <another-session-id>. Garder les deux côtés : démarrez une autre chaîne avec watch chain new <new-chain-name> et laissez les enregistrements d'origine intacts. Zéro octet sans sauvegarde : il ne reste rien à récupérer, traitez-la comme une nouvelle session.

# 1. Lire le nombre de tours et les avertissements de la pointe de chaîne (depuis v0.1.90) npm run watch -- status --json # 2. Trois voies lorsque la pointe de chaîne est une session vide npm run watch -- adopt <provider> --session <another-session-id> # rattacher à une autre session npm run watch -- chain new <new-chain-name> # démarrer une autre chaîne # 3. Restaurer d'abord depuis une sauvegarde, puis réessayer la reprise npm run watch -- switch <provider>
Limites

1. Watch ne reconstruit pas l'historique : une session à 0 tour ne peut revenir que de votre propre sauvegarde. 2. Watch ne supprime ni ne répare jamais un fichier de 0 octet de lui-même ; c'est votre fichier de session natif, et la décision de le restaurer ou de l'abandonner vous revient. 3. Une session lisible à 0 tour n'est pas forcément un contenu effacé : watch new crée exactement cette forme, jugez donc d'après le contexte, pas d'après le nombre seul. 4. Ces divulgations proviennent de la lecture de fichiers locaux ; elles ne garantissent pas que le client natif ouvrira la session, et l'acceptation par le client reste consignée par version et par plateforme.

Questions fréquentes

Watch a-t-il perdu l'historique lorsque la reprise a ouvert une session vide ?

Généralement non. Watch lit d'abord la source et ajoute à la cible avec des gardes d'écriture et des écritures atomiques ; une session à 0 tour est le plus souvent vide dès le départ (une nouvelle session de watch new) ou a été effacée ou tronquée auparavant. Pour savoir si une écriture de Watch en est la cause, comparez le nombre de tours et les warnings du résultat de passation avec votre fichier de sauvegarde.

Quelle est la différence entre 0 tour et 0 octet ?

0 tour signifie que le fichier est lisible et a un en-tête de session valide mais aucune conversation ; ce peut être une nouvelle session ou seulement un en-tête factice restant. 0 octet signifie que le fichier lui-même est vide, à cause d'un processus tué, d'un disque plein ou d'une écriture partielle, et même les métadonnées de session peuvent manquer. Le premier n'a peut-être simplement pas commencé ; le second doit vous conduire d'abord aux sauvegardes.

Watch peut-il restaurer automatiquement une session effacée ?

Non. Watch ne fait que lire et écrire des fichiers de session locaux. Il n'a pas de sauvegarde d'historique et n'invente pas de conversation. La récupération vient de votre propre sauvegarde (Time Machine, copies hors du dépôt, historique de l'éditeur) ; vous reprenez après avoir restauré le fichier.

Claude Code supprime-t-il les anciennes sessions de lui-même ?

Oui. cleanupPeriodDays vaut 30 jours par défaut dans la référence officielle des réglages ; après le début d'une session, Claude Code purge en arrière-plan les transcriptions plus anciennes, et les sessions expirées cessent d'apparaître dans /resume. La clé est admise dans tout fichier de réglages, si bien que les réglages de projet peuvent écraser ceux de l'utilisateur. watch doctor lit sans écrire vos réglages utilisateur, les réglages de projet du répertoire courant et les réglages locaux à la racine du dépôt, mais --settings et les réglages gérés sont hors périmètre ; le rapport n'est donc pas la valeur effective. Augmenter la valeur ne réduit que les suppressions futures ; elle ne peut pas ramener des fichiers déjà supprimés.
