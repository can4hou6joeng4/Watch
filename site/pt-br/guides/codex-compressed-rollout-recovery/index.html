Sessões do Codex reduzidas a .jsonl.zst: limites de leitura e recuperação no Watch

Depois que o Codex comprime uma thread local, o rollout só permanece como .jsonl.zst; o Watch não lê o formato comprimido, então a sessão não aparece em nenhuma lista. Use o watch doctor para ver a contagem de não atribuíveis e continue a thread no Codex para disparar a reexpansão. Uma cópia de 0 byte perdeu o conteúdo; restaure de um backup. Não apague nem renomeie o arquivo .zst.

O Watch lê arquivos rollout .jsonl descomprimidos em ~/.codex/sessions. Depois que o Codex comprime uma thread local, o .jsonl original some e resta apenas um .jsonl.zst de mesmo nome; essas sessões não podem ser listadas, analisadas nem transferidas. O watch doctor e os comandos de listagem divulgam a contagem em vez de fingir que não existem. Se o Codex comprimiu o arquivo e a cópia está intacta, tente continuar a sessão no Codex e verifique se o .jsonl reaparece.

Publicado: 2026-11-23 Atualizado: 2026-11-23 Aplica-se a: Watch v0.1.492
Distinção principal

O Watch lê arquivos descomprimidos como ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl. Depois que o Codex comprime uma thread local, o arquivo original some e resta apenas um .jsonl.zst de mesmo nome no mesmo diretório. O Watch não descomprime nem reescreve, e não relata o ilegível como inexistente: listas, status, doctor e search divulgam a contagem e dizem que esses arquivos não podem ser atribuídos a nenhum diretório.

O Codex guarda a atribuição da sessão no campo cwd da primeira linha session_meta, e essa linha não pode ser lida em uma cópia comprimida. Por isso o Watch não consegue dizer a qual diretório de trabalho a sessão pertence. É exatamente o que a contagem de não atribuíveis no watch doctor e o campo unattributable no watch sessions relatam: não é um erro, mas arquivos que existem sem que esta versão consiga ver dentro. Históricos comprimidos grandes podem gerar uma contagem alta, e isso é esperado.

Uma cópia tem dois estados com próximos passos opostos. Para uma cópia não vazia, continuar a sessão no Codex pode reexpandi-la para .jsonl se o Codex criou a compressão e a cópia está intacta. O Watch consegue ler o arquivo simples depois disso. Uma cópia de 0 byte perdeu o conteúdo; reexpandir não traz a conversa de volta, restaure de um backup ou trate como nova sessão. O Watch só faz stat da existência e do tamanho zero da cópia; ele nunca a abre nem descomprime, e é por isso que a divulgação é condicional: só vale para compressão do Codex intacta.

  1. Passo 1: verificar a contagem e o formato dos arquivos

    Execute watch doctor --json. Para codex, count inclui apenas sessões legíveis, enquanto unattributable conta arquivos cujo diretório não pode ser lido, como cópias comprimidas. A saída de texto mostra o total de não atribuíveis ao lado da contagem de sessões. watch sessions --json e watch recent --json trazem o mesmo campo. O aviso nomeia o formato: uma cópia comprimida .jsonl.zst de mesmo nome, ou uma cópia de 0 byte de mesmo nome. Os dois pedem próximos passos diferentes.

  2. Passo 2: distinguir cópias não vazias de cópias de 0 byte

    Encontre o .jsonl.zst correspondente. Um arquivo não vazio ainda tem bytes, o que não prova que está intacto ou que pode ser descomprimido. Uma cópia de 0 byte não tem conteúdo recuperável; procure um backup. Se a sessão for uma ponta de cadeia inutilizável, watch doctor --json mostra o caminho da cópia em store.brokenTips[].compressedPath e define compressedEmpty como true para uma cópia de 0 byte. O campo de lista unattributable só relata contagens.

  3. Passo 3: continuar a sessão no Codex

    Abra ou continue a thread no Codex. Se a cópia for compressão intacta de thread local do Codex, o Codex a reexpande para .jsonl. Execute watch sessions depois e a sessão reaparece; status, switch e open também conseguem lê-la. O Watch nunca dispara a reexpansão e nunca toca no .zst.

  4. Passo 4: transferir após a reexpansão

    Com o ID da sessão reexpandida em mãos, use os caminhos habituais: watch open <id> --to <provider> ou watch switch <provider>. O watch prompt também não lê o arquivo comprimido; se você indicar essa sessão, ele relata um erro e não produz documento de transferência.

# 1. Somente leitura: contagem e causa npm run watch -- doctor --json npm run watch -- sessions --json # 2. Encontrar os arquivos (o .jsonl original sumiu, só o .zst resta) ls ~/.codex/sessions/*/*/*/*.jsonl.zst # 3. Continuar a sessão no Codex para reexpandir; depois o Watch consegue listá-la npm run watch -- sessions --json # 4. Transferir após a reexpansão npm run watch -- open <session-id> --to <provider>
Limites e o que não fazer

1. O Watch não descomprime, reescreve nem apaga .jsonl.zst, e não julga se o conteúdo é decodificável; só faz stat de existência e tamanho zero. 2. Um arquivo .zst também pode ser seu próprio arquivo compactado. O Watch não presume que o Codex o criou, então o caminho de reexpansão só vale para compressão intacta de thread local do Codex. 3. Não descomprima à mão e devolva o resultado ao diretório sessions: o Watch não valida arquivos feitos à mão, e a aceitação pelo Codex não tem registro de verificação. 4. Não apague nem renomeie o .zst: são seus dados de sessão nativos, e apagá-lo não deixa caminho de recuperação. 5. Este guia segue arquivos locais e o comportamento de divulgação do Watch. A aceitação de uma sessão reexpandida por um cliente nativo é validada por versão e plataforma separadamente, e este guia não é aceitação nativa.

Perguntas frequentes

O Watch comprime ou apaga minhas sessões do Codex?

Não. A compressão é comportamento do Codex. O Watch não lê, reescreve nem apaga arquivos .zst; listagem e análise usam .jsonl descomprimidos. Uma transferência com escrita para o Codex é separada e pode criar ou atualizar um arquivo de sessão de destino descomprimido.

Por que o doctor diz que o diretório não pode ser atribuído em vez de dizer que o arquivo está comprimido?

Porque o Watch só faz stat do arquivo comprimido e nunca o abre. Ele pode confirmar que o .jsonl original sumiu e que existe um .zst de mesmo nome, e o aviso nomeia esse caso de cópia comprimida, mas não pode confirmar que a cópia decodifica nem ler a primeira linha session_meta que carrega a atribuição. A redação permanece condicional para não atestar um fato não verificado.

Posso descomprimir o .zst de volta para .jsonl por conta própria?

Não recomendado. Esse é o diretório de armazenamento nativo; o Watch não valida arquivos feitos à mão, e a aceitação pelo Codex não tem registro de verificação. O caminho mais seguro é continuar a sessão no Codex e deixar o cliente nativo reexpandir.

Qual é a diferença entre uma cópia de 0 byte e uma cópia intacta?

Uma cópia de 0 byte perdeu o conteúdo; reexpandir não traz a conversa de volta, restaure de um backup ou trate como nova sessão. Uma cópia intacta pode ser reexpandida quando você continua a sessão no Codex, e depois o Watch consegue lê-la.

Essas sessões comprimidas ainda podem ser transferidas para outro agente?

Não diretamente. Reexpanda primeiro no Codex, depois use watch open <id> --to <provider> ou watch switch. Antes de transferir, ainda verifique o ID da sessão e o diretório de trabalho e leia os warnings do resultado.
